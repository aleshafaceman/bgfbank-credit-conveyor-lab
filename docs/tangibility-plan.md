# План осязаемости кабинетов (L3, happy-path)

Статус: **на согласование**. Код кабинетов в этом шаге **не меняется**.

Продукт: залог (`CASHONBAIL` / `FLAT`). Отказ не трогаем. Презентер-флаги («Зелёный скоринг», «Быстрый скоринг», «Сбросить демо», автологин) **не прячем**.

Источники полей: `docs/_LK_KNOWLEDGE_BASE.md`, `docs/katalog-opcij-zalog.md`, `shared/lk-application.js`, выгрузки в `docs/sources/` (СПР `.doc`, Visio, ТЗ Loginom, Skorozvon). Код кабинетов **не меняется**, пока нет ОК на этот план.

Стол сделки (`deal-ops/`) не расширяем. Паспорт сделки по СПР — экран ОЗС **без внешних интеграций**; в кабинете P2 = карточка из полей заявки, не календарь.

---

## 0. Зафиксированные правила

| Правило | Как делаем |
|---------|------------|
| Целевой уровень | **L3 широко**: почти каждый значимый шаг оставляет артефакт |
| L2 без артефакта | профиль, согласия в настройках, каналы уведомлений: смена модели + тост |
| Файлы | в localStorage **не** сырые байты. Метаданные `{ name, mime, size, sha? }` + PDF/preview **на лету** из полей |
| Лимит ~5 МБ | один реестр артефактов, без дублей base64 |
| Раздел | единый **«Документы»** у клиента и менеджера (вместо «Мои отчёты» / разрозненного documents) |
| Повтор | артефакт открывается из раздела и из карточки заявки после reload |
| Happy-path | только успешная ветка; issue-модалки скоринга не сохраняем как отказные дела |

## 1. Модель хранения (реализация после согласования)

Новый ключ `bgfbank_lab_artifacts` (рядом с `bgfbank_lab_applications`). Сброс демо уже чистит `bgfbank_lab_*` — добавить ключ в `resetDemoStorage`.

```json
{
  "id": "art_4421_offer_accepted",
  "appId": "4421-И",
  "kind": "preliminary_offer",
  "title": "Предварительные условия · пакет Рекомендуем",
  "createdAt": "2026-06-15T12:00:00.000Z",
  "actor": "client",
  "source": {
    "file": "js/packages.js",
    "fn": "acceptOfferPackage",
    "fields": ["selectedPackageId", "rate", "payment", "amount", "term", "offerValidUntil"]
  },
  "file": { "name": "offer-4421-I.pdf", "mime": "application/pdf", "size": 18432 },
  "payloadRef": { "appId": "4421-И", "slice": "package" }
}
```

`payloadRef` указывает на уже существующие поля заявки/`lk` — **не копировать** большие JSON дважды. Генератор PDF читает slice и рисует превью.

Общий модуль (предлагаемое место): `shared/lk-artifacts.js`

- `upsertArtifact(partial)`
- `listArtifacts(appId)`
- `openArtifact(id)` → HTML/PDF preview (как сейчас `printOfferPackage`, но с записью в реестр)
- `renderDocumentsSection(role)` — клиент и менеджер

Секция «Документы» в навигации обоих кабинетов. Фильтры: по заявке / по типу. Менеджер видит те же артефакты клиента + свои протоколы.

Оценка объёма на happy-path одной сделки (~25 артефактов × ~0.5–1 КБ метаданных) ≈ **20–30 КБ** + заявка `lk`. Превью не храним.

## 2. L2 (без артефактов) — не раздувать

| Поверхность | Действие | Persist | Подтверждение |
|-------------|----------|---------|----------------|
| Профиль · личные данные | сохранить ФИО/телефон/email в `bgfbank_lab_user` / клиентской карточке | модель | тост |
| Профиль · доходы (ручной ввод суммы) | `borrowers[0].incomes` только если нет ЦП; иначе read-only | модель | тост |
| Настройки · уведомления | объект `user.notify.{sms,email,push}` | модель | тост |
| Настройки · согласия ПДн/БКИ/реклама | `user.consents.{pdn,bki,ads}` + даты | модель | тост |
| Смена пароля / 2FA | уже есть user record | как сейчас | тост |

**Исключение:** сами тексты СОПД/БКИ, которые клиент подписывает **в конвейере заявки**, — это L3 (строки C1, C2 ниже), не настройки профиля.

## 3. Единый каталог артефактов

Приоритет:

- **P0** — без этого руководство снова видит «пустоту» на текущем happy-path кабинетов (вход → пакет → ЕГРН → скоринг → одобрение).
- **P1** — добивает L3 на том же пути (протоколы, разбор ставки, ДУ как документы).
- **P2** — мост к паспорту/КОД, чтобы после approve в кабинете было «что подписали», без стола ОЗС.

Объём: S = 1 экран + генератор из уже лежащих полей; M = новый блок UI + запись нескольких полей; L = согласовать состав после первоисточников (паспорт сделки).

## 4. Что меняется в UI (после согласования, не сейчас)

**Клиент**

- Пункт нав. **Документы** (вместо смысла «Мои отчёты» в профиле).
- Карточка заявки: чеклист документов ведёт в тот же реестр (openArtifact).
- Конвейер: после ЕСИА/оценки/пакета — тост **и** строка в Документах.
- `printOfferPackage` открывает сохранённый C11.
- Загрузка: выбрать файл → видны имя и размер → preview-заглушка.

**Менеджер**

- Пункт нав. **Документы** (общий реестр по выбранной заявке).
- В карточке: ЦП как сейчас + ссылка «открыть выписку».
- Блок разбора ставки §9.
- После прескоринга/скоринга — кнопки «Протокол».
- ДУ: статусы в localStorage; тип подписывать ELMA 0–18 где есть соответствие.

**Не трогать**

- Чекбоксы зелёного/быстрого скоринга, сброс демо, `?demo=1` / `?autologin=1`.
- `renderCpCoverageHTML` остаётся **только у менеджера** (аудит это проверяет). Клиентский C3 — отдельный «человеческий» шаблон из тех же `scopes`, без `cp-profile-btn`.
- Ветку отказа, issue-модалки скоринга.
- `deal-ops/` кроме, возможно, выноса канона `kod.documents` / `du_catalog` в `shared/` (чтение, без смены сценариев стола).

## 5. ДУ: как не выдумать виды

Для L3 на happy-path залога использовать **enum ELMA 0–18**. Кабинетный `allDU` сузить на показе:

| ELMA type | Title (mock) | Когда на happy-path 4421/4636 |
|-----------|--------------|-------------------------------|
| 0 | Предоставить финансовый документ | только профиль ЦП `no_ndfl` (презентер). На зелёном full — **нет** |
| 2 | Документ по объекту залога | ЕГРН (C8) |
| 5 / 18 | брак / нотариальное согласие супруга | **не** включать, пока `marital_status` в FILL_IN = `null` (ЦП семью не отдаёт) |
| 14 | Погашение после сделки | стол, не кабинет |

Остальные du01–du22 (домовая, БТИ, маткапитал, опека…) **не поднимать** в L3, пока нет поля-триггера в `lk`. Иначе снова бутафория.

Persist ДУ: писать в `lk.additional_conditions[]` (уже есть) + статус `pending|received`, не в отдельный RAM `duStorage`.

## 6. Порядок внедрения (когда дадите ОК)

Отдельные логические коммиты, без смешения с потребкредитом.

1. `shared/lk-artifacts.js` + ключ localStorage + сброс демо + секция «Документы» (пустая оболочка).
2. P0 клиент: C1–C8, C10, C11, C13, C15 (конвейер 4421 становится осязаемым).
3. P0 менеджер: M2, M3, M4, M7–M10 (скоринг оставляет протокол и решение).
4. P1: ДУ persist, C9/C14, M1/M6/M11/M12, чистка «Мои отчёты».
5. P2 по отдельному ОК: паспорт сделки M13 + опись КОД C16/M14.
6. `node scripts/pre-release-audit.js` зелёный на каждом коммите; аудит `renderCpCoverageHTML` только в manager — сохранить.

Оценка трудоёмкости: пункты 1–3 — основной объём (хранилище, генератор PDF, две навигации, запись в существующих `acceptOfferPackage` / `applyManager*`). Пункт 5 зависит от первоисточника паспорта.

## 7. Вопросы на согласование

1. **P2 (паспорт сделки / КОД в кабинете)** — делать в этой итерации кабинетов или оставить столу? Стол явно выносит паспорт из АРМ.
2. **Заявка 4636-И** (TrustGate lab) скрыта от клиента. Показывать клиенту человеческие артефакты ЦП на **4421-И**, а 4636 оставить менеджерским стендом?
3. **Три пакета runtime** vs полный каталог `PKG_*` — L3 фиксирует то, что реально выбирается сейчас (`RECOMMENDED` / `SPEC_4_0` / `NO_INSURANCE`), без новых карточек.
4. Когда доедут скилл / ЦФТ 10–15 / SMSTraffic — отдельные артефакты (message_id, OpenAccount) **не ломая** P0.
5. Overlay сейчас показывает PTI/DTI — в протоколе L3 писать **ПДН `getPdn`**, не выдавать PTI за поле СПР.

Если пункты 1–3 ок — следующий шаг: реализация P0, без потребкредита и без редизайна форм.
