# Сведения об объекте залога: откуда берутся данные

Итоговая справка по всем источникам данных об объекте залога: что даёт каждая система, что именно она возвращает, где границы и что осталось выяснить.

Дата: 22.09.2026. Статус: **справочная записка, не решение**. Изменения в код и макеты по этому документу не вносились.

Документ объединяет два исследования: разбор внутренних материалов репозитория и поиск официальной спецификации ЕГРН в открытых источниках.

## 1. Зачем документ

В лабораторном макете ([`form-pledge/`](../../form-pledge/), экран «Карточка ЕГРН») сведения об объекте показываются одной карточкой: адрес, тип, площадь, этаж, кадастр, доля, правообладатель, обременения. Карточка заполняется мгновенно по введённому кадастровому номеру.

Такого канала не существует в том виде, как он нарисован. Ниже — что есть на самом деле.

## 2. Три группы данных и три разных источника

Ключ к теме: сведения об объекте делятся на группы, и у каждой **свой** источник. Путаница возникает, когда их считают одним набором.

| Группа | Состав |
|---|---|
| Адрес и характеристики | адрес, тип объекта, площадь, этаж, этажность, число комнат, год постройки, материал стен |
| Кадастровый номер | кадастр квартиры (не здания) |
| Юридические факты | правообладатель, доля, обременения |

**Юридические факты не даёт ни один «сервисный» источник.** Оценщик оценивает, реестр подтверждает право.

## 3. Сводная таблица: кто что отдаёт

| Сведение | Источник | Как получается | Статус |
|---|---|---|---|

| Адрес (подсказки) | DaData | HTTP-запрос | Контракт есть |
| Площадь | МО (`flat.area`), DaData (`area`) | HTTP-запрос | Есть |

| Тип дома, материал стен | МО (`bld.bldType`, `bld.wallMaterial`) | HTTP-запрос | Есть |

## 5. Мобильный оценщик — характеристики и цена

Два разных API:

- **Gate / Lookup** — `https://api.ocenka.mobi/v1/appraise/flat?address=...`, справочник. Stateless, задача в кабинете МО **не создаётся** (`mobile-appraiser-integration.md`, §5.4). Вызывается при смене адреса: `apply_changes_to_product()` → `ExpressAppraiser.apply()`.
- **Express** — `express.ocenka.mobi`, создаёт задачу.

### 5.1. Маппинг ответа Lookup в поля заявки

(`mobile-appraiser-integration.md`, §5.2)

| Поле продукта | Путь в ответе МО |
|---|---|
| `floor` | `flat.floor` |
| `rooms` | `flat.rooms` |
| `area` | `flat.area` |
| `number_of_storeys` | `bld.maxFloor` |
| `construction_year` | `bld.bldYear` |
| `cadastral_or_conditional_number` | `flat.cadNum` |
| `premise_material` | `bld.bldType` (маппинг в ELMA-enum) |
| `building_price` | `stats.price` — **только для партнёра** |
| `appraisal_building_price` | `stats.price` — **только для партнёра** |

### 5.2. Что ещё в ответе Gate

(`get_appraise_flat.md`)

- `address` — нормализованный адрес;
- `bld` — координаты, этажность, год, материал стен, `bldType`, `cadNum` **ОКС**, фото, станции;
- `bld.quality` — точность геокода: `success` дом / `warning` улица / `danger` НП;
- `stats.priceRange` — квартильный диапазон;
- `requestId`.

Обратный метод: `GET https://api.ocenka.mobi/v1/cad/search?cadNum=...` — по кадастру находит адрес. Применяется в `bring_to_underwriting`, **если адреса нет, а кадастр есть**.

### 5.3. Оговорка по кадастру квартиры

`flat.cadNum` приходит **не всегда** (`get_appraise_flat.md`):

- в Gate **нет** `fiasId` и `cadNum` — они есть у `/search/bld` и `/find/flat`;
- блок `flat` может отсутствовать, если не передан `forceFlat` (по умолчанию поиск квартиры в Росреестре идёт только когда не передана `area`);
- в схеме swagger от 2026-01-28 и в живом ответе без `forceFlat` блока `flat` может не быть — в документе стоит прямой запрет «не выдумывать».

**Вывод:** кадастр здания (`bld.cadNum`) доступнее, чем кадастр квартиры (`flat.cadNum`). Для залога нужен второй.

## 6. DaData — адрес и площадь, не оценка

Подсказки адреса и `building_price` (цена за м² × площадь). В интеграциях зафиксировано прямо:

> «DaData — подсказки адреса, это не оценка.»
> — `lk-external-integrations.html`, стр. 382

В кабинете на первом экране залога из ответа берётся **только площадь**; `building_price` из DaData там не сохраняется (`mobile-appraiser-integration.md`, §8). Отдельно: при вводе адреса используется `GET /api/products/calculator/building_price` — это DaData, **не** Мобильный оценщик.

## 7. ЕГРН через СМЭВ — спецификация найдена

### 7.1. Правовая основа: состав сведений и формат

Первоисточник — **приказ Росреестра от 04.09.2020 № П/0329** (действующая редакция от 07.04.2026). Он утверждает формы выписок, состав сведений и требования к электронному формату: [sudact.ru — приказ П/0329](https://sudact.ru/law/prikaz-rosreestra-ot-04092020-n-p0329-ob/prilozhenie-n-13_1/trebovaniia-k-formatu-dokumentov-soderzhashchikh/).

Для залога релевантны три вида выписок из двадцати приложений приказа:

| Приложение | Выписка |
|---|---|
| **№ 2** | об основных характеристиках и **зарегистрированных правах** на объект недвижимости |
| **№ 1** | об объекте недвижимости (полная) |
| **№ 12** | об установленных в пользу отдельного лица **ограничениях прав и обременениях** |

**Формат — XML, а не JSON:**

> «Документы, содержащие сведения ЕГРН, направляемые в форме электронного документа, представляются в виде **XML-документа**, созданного с использованием XML-схем и обеспечивающего считывание и контроль представленных данных»
> — приказ П/0329, приложение № 13, п. 236

Это принципиально: даже при живом запросе приходит **документ**, а не готовые поля. Отличие от AS-IS только в том, что файл приходит по каналу, а не от клиента.

### 7.2. API: что вызывается

Документация СМЭВ-шлюза (Platform V SMEV Gateway) описывает сервис асинхронно — отправка запроса и отдельное получение результата.

**Отправка запроса:**

```
POST /rrtr/egrn/extract/1/1/1
```

Тело: `header` (`EGRNRequestHeader`), `declarant` (`EGRNRequestDeclarant`), `requestDetails` (`RequestDetails`), `deliveryDetails`, `statementAgreements`, `region`, `senderType` (`MFC | VEDOMSTVO | OTHER`).

**Получение результата:**

```
GET /rrtr/egrn/extract/1/1/1?requestId=...
```

Ответ: `requestNumber`, `attachment`, `attachmentsInfo` — то есть **вложение**, а не структурированные поля.

Доступны две версии сервиса:

- [v2.5.0](https://platform-docs.v-serv.ru/online-documentation/home/user/process-management/smev/2.5.0/api-get/predostavlenie-svedenij-soderzhashihsya-v-edinom-gosudarstvennom-reestre-nedvizhimosti/);
- [v1.1.1 в шлюзе 3.4.0](https://platform-docs.v-serv.ru/online-documentation/home/user/process-management/smev/3.4.0/api-get/predostavlenie-svedenij-soderzhashihsya-v-edinom-gosudarstvennom-reestre-nedvizhimosti-v111/) — добавлен параметр `version: V1_1 | V1_2 | V1_3` и модель `EGRNGenuinenessOfSignature` (проверка подлинности подписи).

Отдельный метод для земельного участка: `POST /rrtr/egrn/params-land/1/1/1` с моделями `BaseParamsRightHolder`, `IndividualHolder`, `LegalHolder`, `BaseParamsRightType` — там правообладатель и вид права вынесены в отдельные модели.

### 7.3. В ответе есть правообладатель и обременения

Состав моделей ответа (v1.1.1) отвечает на главный вопрос — нужные данные в спецификации **есть**:

- `EGRNSubjects` — субъекты права;
- `EGRNBasicStrictDocument` — правоустанавливающий документ;
- `EGRNBasicServiceInfo` — базовая служебная информация;
- `EGRNPayInfo`, `EGRNNotarization`, `EGRNNotaryInfo` — оплата и нотариус;
- `EGRNIssuerInfo`, `EGRNFIO` — орган выдачи и ФИО;
- `EGRNAddressElement`, `EGRNHouse`, `EGRNApartment`, `EGRNAddressCityBase` — адрес: дом, **квартира**, город;
- `EGRNGenuinenessOfSignature` — подлинность подписи.

То есть правообладатель, объект права и обременения приходят по этому каналу. Это снимает главный пробел: **живой способ получить их, кроме OCR, существует**.

### 7.4. Второй канал СМЭВ: через согласие ЕСИА

Путь, который ближе к клиентскому сценарию — вид сведений «Запрос персональных данных пользователя ЕСИА при наличии его согласия» версии 1.0.2, с `dataType = REG_REALESTATE` и обязательным `idPermission` (идентификатор согласия пользователя): [info.gosuslugi.ru](https://info.gosuslugi.ru/articles/%d0%9f%d0%be%d0%bb%d1%83%d1%87%d0%b5%d0%bd%d0%b8%d0%b5_%d1%81%d0%b2%d0%b5%d0%b4%d0%b5%d0%bd%d0%b8%d0%b9_%d0%be_%d0%bd%d0%b5%d0%b4%d0%b2%d0%b8%d0%b6%d0%b8%d0%bc%d0%be%d1%81%d1%82%d0%b8_%d1%87%d0%b5%d1%80%d0%b5%d0%b7_%d0%b2%d0%b8%d0%b4%d1%8b_%d1%81%d0%b2%d0%b5%d0%b4%d0%b5%d0%bd%d0%b8%d0%b9_%d0%a1%d0%9c%d0%ad%d0%92/).

Ответ приходит файлами: `RE_EXTRACTION_<oid>_6142800.xml` и `ProofData_...xml` — снова **XML-вложения**. Этот канал требует согласия клиента и его `idPermission`, то есть ложится на шаг «Согласия → Госуслуги».

## 8. OCR Basis — канал настроен, но поля ЕГРН не разбираются

### 8.1. Как подключено

По конфигу и коду `bgf-backend/recognition`:

| Что | Значение | Где |
|---|---|---|
| Хост | `https://api.doc.basis.center` | `recognition_api/etc/brokers.yml` |
| Маршрут распознавания | `/recognize?async=1` | там же |
| Пресет по умолчанию (прод) | `BGF.passport23` | там же |
| Пресеты в коде | `passport.pilot`, `BGF.passport23`, **`BGF.EGRN`**, `BGF.mortgage`, `selector` | `broker/parsers/bazis.py`, стр. 41–52 |
| Типы документов в разборе | `td`, `tk`, `inn`, `sbf`, `2ndfl`, `snils`, `passport`, **`egrn`** | там же, стр. 12–21 |
| Форма запроса | multipart `files` + `preset` | тесты `recognition_tests/tests/test_01…test_10` |

### 8.2. Ключевая находка: из ЕГРН берётся только номер выписки

В `broker/parsers/bazis.py` обработка ЕГРН есть в двух местах, и оба почти пустые:

```python
def prepare_egrn_result(solution: dict) -> dict:      # строка 71
    egrn_response = {"type": "egrn"}
    if "egrn" not in solution.get("explained", {}):
        return egrn_response
    egrn_response["numberEgrn"] = solution["explained"]["egrn"]["numberEgrn"]
    return egrn_response                              # только номер
```

```python
def egrn_parser(document):                            # строка 266
    document_fields = {}
    document["fields"] = document_fields              # пустой набор полей
    return document
```

Для сравнения: у паспорта (`prepare_passport_result`), ИНН (`inn_parser`), СНИЛС (`snils_papser`), трудовой (`tk_parser`), 2-НДФЛ (`ndfl2_parser`) разбор полей реализован. **У ЕГРН — нет.**

### 8.3. Что это значит

1. **OCR технически работает с выпиской ЕГРН** — пресет `BGF.EGRN` существует, документ распознаётся, в ответе есть структура `explained.egrn` как минимум с номером выписки.
2. **Но юридические факты сейчас не извлекаются.** Правообладатель, доля и обременения, если и приходят от Basis, то **игнорируются** нашей интеграцией. Это и есть причина, по которой этих данных нет ни в кабинете, ни в заявке.
3. Вопрос распадается на два:
   - **технический** — настроить разбор полей в `prepare_egrn_result` / `egrn_parser`, если Basis их возвращает (это правка парсера, не новая интеграция);
   - **договорной** — получить у Basis полный состав полей для `BGF.EGRN`.

## 9. Клиент или менеджер — кадастр вручную

В кабинете `product.cadastral_number` — поле заявки, которое «часто `null`» (`_LK_KNOWLEDGE_BASE.md`, стр. 372). ЕГРН там числится как `missing`:

> «Выписка ЕГРН — всегда `missing` («Нужен кадастр, не ЦП»)»
> — `_LK_KNOWLEDGE_BASE.md`, стр. 418

Кадастр приходит от клиента или из документа, но **не из цифрового профиля**: квартиры ЕСИА не отдаёт.

## 10. Чего не даёт ни один источник

| Сведение | Почему нет |
|---|---|
| Правообладатель, доля | Только ЕГРН: СМЭВ или выписка |
| Обременения | Только ЕГРН |
| Год постройки | МО отдаёт `bld.bldYear`, но он **может быть `null`** |
| Кадастр квартиры гарантированно | МО отдаёт `flat.cadNum` при `forceFlat`; иначе только кадастр здания |
| Право и обременения из OCR **сейчас** | Парсер ЕГРН возвращает пустые поля (§8.2) |

## 11. Кто чему источник истины

- **Стоимость для сделки** — официальный отчёт оценщика (`AppraisalPledgeCost`), не `stats.price`. Это разные величины, и расхождение между ними в документах отмечено как нормальное (`mobile-appraiser-integration.md`, §10).
- **Характеристики объекта** — МО Gate / Lookup.
- **Право и обременения** — ЕГРН: выписка по СМЭВ либо, если канал не подключён, выписка клиента с разбором.
- **Кадастр квартиры** — МО `flat.cadNum`, иначе из выписки, иначе ввод клиента.
- **Решение по клиенту** — не МО. Оценщик отвечает за цену объекта, а не за кредитное решение.

## 12. Расхождение с макетом

Экран «Карточка ЕГРН» **преувеличивает доступность данных**:

| Поле в макете | Откуда в реальности |
|---|---|
| Адрес | МО (нормализованный) |
| Тип | МО (`bld.bldType`) |
| Площадь / этаж | МО (`flat.area`, `flat.floor`) |
| Кадастр | МО `flat.cadNum` при `forceFlat`, иначе из выписки или ввод |
| **Правообладатель** | **ЕГРН: СМЭВ или разбор выписки** |
| **Совпадение с ЕСИА** | вычисляется банком, отдельного источника нет |
| **Доля** | **ЕГРН** |
| **Обременения** | **ЕГРН** |
| Цена | МО (`stats.price`), но для сделки — официальная оценка |

Макет показывает единый мгновенный ответ там, где в реальности два разных механизма: справочный запрос к оценщику и получение документа из реестра.

## 13. Что нужно решить

1. **Подключать ли ЕГРН через СМЭВ.** Спецификация есть, модели содержат нужные данные, но результат — XML-документ, значит в конвейере нужен разбор XML (адаптер). Требуется статус участника информационного взаимодействия и подключение вида сведений.
2. **Доступны ли выписки кредитной организации.** Выписка № 2 в приказе описана как «по запросу органа власти». Может ли банк запрашивать её напрямую или только через витрину ЦФТ / сервис-посредник — не подтверждено.
3. **Запросить у Basis состав полей `BGF.EGRN`.** Если вендор отдаёт правообладателя, долю и обременения, их можно начать разбирать правкой парсера — это дешевле подключения СМЭВ.
4. **Надёжность кадастра квартиры от МО.** Полагаться на `flat.cadNum` с `forceFlat` или считать источником выписку.
5. **Где по процессу проверять право и обременения** — до подачи заявки или на АПЗ, где комплект документов уже в работе и действует барьер паспорта сделки.
6. **Нужно ли тянуть кадастр из ЦФТ**, если клиент уже обслуживается в банке и объект там известен.

## 14. Что проверено, а что нет

**Проверено — в материалах репозитория:**

- маппинг полей МО Lookup → заявка (`mobile-appraiser-integration.md`, §5.2);
- состав ответа Gate, оговорки по `forceFlat`, блоку `flat` и `bld.cadNum` (`get_appraise_flat.md`);
- состав Express и закомментированные поля ТЗ (`express-api.md`);
- роль DaData как подсказок адреса (`lk-external-integrations.html`, стр. 382);
- ЕГРН как «файл + OCR, не СМЭВ» в AS-IS (`lk-external-integrations.html`, стр. 578; `_LK_KNOWLEDGE_BASE.md`, стр. 125, 597);
- кадастр «часто `null`», ЕГРН как `missing` (`_LK_KNOWLEDGE_BASE.md`, стр. 372, 418);
- **интеграция с Basis и отсутствие разбора полей ЕГРН** — прочитано в коде (§8.2);
- настройки брокеров распознавания (`recognition_api/etc/brokers.yml`).

**Проверено — в открытых источниках:**

- приказ Росреестра П/0329: виды выписок (приложения № 1, 2, 12) и требование XML-формата (приложение № 13, п. 236);
- эндпоинты и модели сервиса ЕГРН в СМЭВ-шлюзе (v2.5.0 и v1.1.1), включая `EGRNSubjects` и `EGRNBasicStrictDocument`;
- канал через согласие ЕСИА: `dataType = REG_REALESTATE`, обязательный `idPermission`, ответ XML-файлами.

**Не выяснено:**

- **полный состав полей моделей** `EGRNSubjects`, `RequestDetails`, `RequestObject` — документация отдаёт оглавление усечённо, нужен Swagger;
- **права кредитной организации** на запрос выписок через СМЭВ;
- **реквизиты вида сведений** (идентификатор услуги, версия, ТС) — на портале ситуационного центра есть, конкретный ID для ЕГРН не открыт;
- **XML-схемы выписок** — приказ на них ссылается, сами схемы не скачаны;
- **состав полей, которые Basis возвращает по `BGF.EGRN`** — документация `doc.basis.center` закрыта для статического чтения, а в репозитории **нет ни одного образца ответа с ЕГРН**: из девяти файлов в `recognition_api/broker/tests/response_samples/` ни один не содержит `egrn`. Образцы есть только по паспорту, 2-НДФЛ, ИНН, СНИЛС, трудовой книжке и форме банка (`sbf`);
- **что содержит `explained.egrn` целиком** — в коде видно только чтение `numberEgrn`;
- спека MFMS и стадии официальной оценки (P1) — по инвентарю источников помечены как отсутствующие.

## 16. Итог одной фразой

Характеристики и цена объекта берутся **запросом к Мобильному оценщику** (плюс DaData для адреса), кадастр квартиры — оттуда же при `forceFlat` или из выписки, а **право и обременения — только из ЕГРН**: либо выпиской по СМЭВ (спецификация существует, модели содержат нужные данные, но результат приходит XML-документом), либо выпиской клиента с разбором OCR — при том что **сейчас в коде разбор полей ЕГРН не реализован**, извлекается только номер выписки.
