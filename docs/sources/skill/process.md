# Процесс: лид → выдача

Источник AS-IS: регламенты `Старый КК`, `Elma3StageStatusEnum` 0–52, карточки ELMA (лид + заявка), БТ/Visio открытия счёта. TO-BE повторяет те же этапы в Conveyor; после КОД возможен ранний sidecar `deal-ops`.

## Два объекта в ELMA

Конвертация: лид → заявка (`CreateFullApplication` / `SendLeadConvertationStatus`). После этого конвейер банка живёт на заявке. Карточка лида может ещё копить короткие процессы (дубль, архив коротких заявок) — это не стадия сделки.

### Состав лида

- Карточка: роль заявителя, канал, подразделение, ответственные, партнёрская опция
- Продукт: цель, сумма, срок, тип/регион залога, доход, страхование
- Персданные и СОПД
- Прескоринг: скоринги, КИ, ФССП, ПДН, ID в ЦФТ
- Задачи короткой заявки: дубль, распределение, первичная проверка, идентификация, экспресс-оценка
- История запросов: Loginom, ЦФТ, B2B, МО

### Состав заявки

- Шапка: номер, продукт, канал создания, статус/стадия, ответственные, КВ
- Параметры кредита и залога, ЕГРН, отчёт об оценке
- Документы (клиент и объект)
- Задачи и экземпляры процессов (единица работы банка)
- Итог АНД / АПЗ / СБ
- Доп. условия (чеклист до заключения / аккредитива / выдачи)
- Паспорт сделки
- История статусов
- История запросов заявки (Loginom, ЕГРН, ЦФТ, B2B)

## Этапы

```
Лид
  вход (cabinet шаг 1 «Заявка» или Reception)
       → дубль → прескоринг (кнопка ЛК «Получить пре-оффер» → Loginom preScore + Solver-пакеты на шаге 2)
       → экспресс-оценка (МО) → идентификация (ЦФТ CheckData)
       → prior_approve | очередь менеджера | отказ | закрытие

Заявка (после конвертации)
  сбор документов → заполнение заёмщика ∥ заполнение залога
  → процессинг заёмщика → СБ → АНД
  → процессинг залога → СБ (если ещё не пройдена) → АПЗ
  барьер: client_approved AND pledge_approved
  → паспорт сделки → процессинг КОД (ОПС)
  → КОД сформирован  →  [ELMA больше не владеет офисом]
       deal-ops: снимок → идентификация ОЗС → ДУ
         → FindRetailAccount → автопроверки (если счёт не open)
         → заявление на счёт (sms|paper) → подписание КОД (paper|smartdeal)
         → ДБО
  → выдача (ОБУКО в ЦФТ на известный счёт) → регистрация закладной → архив
```

В split два inbox'а. В combined клиенту не выдают квесты `collect_docs` / `fill_*`, но очереди АНД и АПЗ остаются разными.

Офисный happy-path: клиент остаётся у ОЗС. Паспорт сверяют со снимком. СОПД не переподписывают датой визита. ОПЕРУ — только если автопроверка дала `error`. Подробности: [deal-ops.md](deal-ops.md).

## Что обычно ломает «прямую линию»

Это ожидаемое поведение банка, закладывай в схемы и статусы:

- Отказ банка по клиенту или залогу → закрытие или повтор с правом пересмотра
- Доработка продаж / процессора / АНД / АПЗ
- Добавление созаёмщика — на быстрой заявке кнопка шага 1, не шаг 3 «Документы»; дальше отдельный мини-конвейер заполнение→процессинг→СБ→АНД
- «Не принять оценку» — цикл, нужен лимит, не бесконечность
- ДУ часть снимается на заключении, часть на аккредитиве/выдаче после регистрации
- Возврат комплекта на процессинг КОД (`kod_revision` / ELMA 30)
- Отказ клиента от подписи (`client_refused` / ELMA 38)
- После «кредит выдан» ещё хвост: Росреестр, закладная, бумажное досье, архив
- Веер задач «назначить ответственного» / вебхуки / генерация шаблонов — шум оркестрации, не новые бизнес-этапы
- AS-IS офиса: второе окно ОПЕРУ и повтор паспорта — **это обрыв конвейера**, не норма TO-BE

## Правила оркестратора

1. Активный дубль блокирует новый контур; разблокировка — явная операция с аудитом.
2. Один исход заполнения заёмщика: процессинг **или** доработка **или** отказ (не параллельные статусы).
3. Все заявки через СБ; цикл доработки со счётчиком и эскалацией.
4. Дата сделки: Москва — график ОЗС, регион — календарь; это конфиг, не ветка BPM. Календарь паспорта **не** в `deal-ops` v1.
5. ПИК vs не-ПИК и момент госрегистрации — ветки `signing` → `issue`.
6. После «КОД сформирован» источник правды офиса — снимок, не повторный ввод в ELMA/ЦФТ.
