# Happy-path v1: ЕСИА + один объект = combined

Канон входного сценария формы подачи. UX-набросок: [лаб v1.2](https://github.com/aleshafaceman/bgfbank-credit-conveyor-lab/releases/tag/v1.2-lab). **Поля экранов:** [esia-screens.md](./esia-screens.md). Ландшафт: [to-be-overview.md](./to-be-overview.md). Стадии: [to-be-process.md](./to-be-process.md). Адаптеры: [to-be-integrations.md](./to-be-integrations.md).

Зафиксировано в v1:

1. **Цели согласия ЕСИА / ЦПГ** — финансовые услуги, нефинансовые услуги, запрос кредитного отчёта (БКИ). Не «паспорт + недвижимость».
2. **Объект залога** — клиент вводит **кадастровый номер**, Conveyor запрашивает **ЕГРН** (СМЭВ Росреестр). Не список из цифрового профиля.
3. **Один подтверждённый объект** (только залог своей квартиры, без рефина) → `route_mode = combined`. Заёмщик и залог идут одним маршрутом, клиентские этапы заполнения не создаются.

## 1. Граница продукта

| Входит в v1 | Не входит (сход или следующая версия) |
|-------------|----------------------------------------|
| Кредит под залог **своей** квартиры / апартаментов | Покупка |
| Клиент сам в форме (`channel=b2c`) | **Рефинансирование** — v2, не этот документ |
| | Дом+земля, коммерция, доля без 100% |
| | Подача брокером через cabinet |

## 2. Согласия и ЕСИА

Два слоя, не путать:

| Слой | Что это | Зачем |
|------|---------|-------|
| Согласие банка (`consent`) | текст 152-ФЗ / БКИ в форме | юридический акцепт банка, как AS-IS `PERSONAL_DATA` + `CREDIT_HISTORY` |
| Цели ЦПГ в ЕСИА | `purposes` / `sysname` подключения банка | что Госуслуги разрешают запросить из цифрового профиля |

Мнемоники `purposes` / `sysname` брать из карточки подключения банка к ЦПГ, не выдумывать. Ниже — доменные имена.

### 2.1 Цели ЕСИА / ЦПГ (факт банка)

| Доменный код | Цель | Что даёт |
|--------------|------|----------|
| `CPG_FIN` | финансовые услуги | сведения профиля для оказания фин. услуги (кредит) |
| `CPG_NONFIN` | нефинансовые услуги | те же сведения по второй цели подключения банка |
| `CPG_BKI` | запрос кредитного отчёта | согласие на КО / БКИ через инфраструктуру ЦПГ |

Без всех трёх целей редиректа в ЕСИА нет. Частичный отказ = сход на ручную анкету, не «урезанный прескоринг».

Согласие банка `CREDIT_HISTORY` — тот же смысл, что `CPG_BKI`: не плодить второе «согласие на БКИ» с другим текстом. `PERSONAL_DATA` остаётся текстом банка (152-ФЗ), это не цель ЦПГ.

Снято с канона (ошибка черновика): `ESIA_ID_DOC`, `ESIA_REAL_ESTATE` как отдельные scope.

### 2.2 Что ожидаем после акцепта фин/нонфин

Типичный состав ЦПГ по этим целям (уточняется по видам сведений в карточке банка):

- личность: ФИО, ДР, паспорт, ИНН, СНИЛС, адрес;
- вход: `esia_sub`.

Телефон уже есть из OTP; мобильный / email из профиля — сверка, не замена сессии.

Это **не** список объектов залога.

### 2.3 Сведения о недвижимости: кадастр + ЕГРН

Источник объекта v1 **зафиксирован**: клиент вводит кадастровый номер → адаптер `EgrnAdapter` (`FetchEgrnByCadastral`) → выписка ЕГРН. ЕСИА квартиру не отдаёт; список объектов из ЦПГ в v1 не строим.

| Что берём из ЕГРН | Зачем |
|-------------------|--------|
| Адрес, вид объекта, площадь, этаж (если есть) | карточка залога, МО, Solver |
| Право, доля, правообладатель | шлюзы v1 и сверка с ФИО из ЕСИА |
| Обременения | стоп рефина / чужого залога |

Мобильный оценщик по-прежнему даёт **цену**, не право. Выписка файлом + OCR — сход, если СМЭВ недоступен, не основной путь.

`verified_via` на заёмщике: `esia`. На залоге: `egrn`.

Сверка «своя квартира»: правообладатель в ЕГРН сопоставляется с личностью ЕСИА (ФИО, при наличии — паспорт). Расхождение — сход (чужой объект / опечатка кадастра / задача `sales`), не combined.

### 2.4 Запросы после callback

| Команда | Адаптер | Результат |
|---------|---------|-----------|
| `EsiaExchangeCode` | EsiaAdapter | токены, `esia_sub`, поля личности по фин/нонфин |
| `FetchCreditReportConsent` | EsiaAdapter / ЦПГ | факт цели `CPG_BKI` (сам отчёт БКИ по-прежнему тянет Loginom) |
| `FetchEgrnByCadastral` | EgrnAdapter (СМЭВ Росреестр) | право, доля, обременения, адрес, площадь |
| `LookupQuote` | МО | рыночная цена |

Клиент на экране 5 вводит кадастр и подтверждает карточку из ЕГРН. Прямого вызова Росреестра из UI нет. Loginom запрашивает БКИ сам; ЕСИА даёт согласие/цель, не HTML отчёта НБКИ.

## 3. Правило combined

Срабатывает **один раз**, когда клиент подтвердил карточку ЕГРН (экран 5), до прескоринга.

```
ЕСЛИ product_intent = cash_on_pledge
И клиент ввёл кадастровый номер
И FetchEgrnByCadastral успешен
И выбран ровно один объект
И объект проходит шлюзы v1
ТО route_mode := combined
   pledge_id := выбранный
   не создавать клиентские задачи collect_docs, fill_borrower, fill_pledge
```

Шлюзы объекта v1 (иначе сход, `combined` не ставить):

- тип: квартира или апартаменты;
- право: собственность, доля = 100%;
- правообладатель сопоставим с личностью ЕСИА;
- нет блокирующего обременения (в v1 залог другого банка не допускается: это рефин, следующая версия);
- есть кадастровый номер;
- МО вернул цену (lookup или express — по конфигу роли `client`).

`split` в этом сценарии не предлагаем: второй объект или созаёмщик = другой сценарий, не v1 happy-path. Рефинансирование на экране 2 — сход, как покупка.

После `PrescoringApproved` и принятия пакета:

```
prior_approve → processing (combined)
  → СБ → АНД + АПЗ по правилам банка
```

Барьер паспорта сделки без изменений: нужны и `client_approved`, и `pledge_approved`. Combined означает **один клиентский вход**, не схлопывание АНД и АПЗ в одну роль.

## 4. Экраны и события Conveyor

Поля и кнопки — [esia-screens.md](./esia-screens.md). Сумма запрашивается на экране 2; срок — в пакете на экране 6.

| Экран | Команда / событие | `stage` |
|-------|-------------------|---------|
| 1 OTP | `ApplicationDraftCreated` | `lead` |
| 2 Цель | `ProductIntentSet` | `lead` |
| 3 Согласия | `ConsentAccepted` (ПДн банка + три цели ЦПГ) | `lead` |
| 4 ЕСИА callback | `EsiaIdentityVerified` | `lead` |
| 5 кадастр | `CadastralEntered` → `FetchEgrnByCadastral` | `lead` |
| 5 карточка ЕГРН | `PledgeSelected` → правило §3 | `lead` |
| ожидание | `RunPrescoring` (Loginom `preScore`) + МО; пакеты — **Solver**, не скоринг | `prescoring` |
| 6 принять пакет | `OfferAccepted` (прескоринговый офер Solver) | `prior_approve` |

Клиент не вызывает Loginom, ЕСИА token endpoint, МО, Росреестр.

## 5. Сходы (не ломают v1)

| Условие | Куда |
|---------|------|
| Нет / невалидный кадастр | повтор ввода |
| ЕГРН недоступен / пустой ответ | задача `sales` или загрузка выписки (OCR) — сход |
| Правообладатель не совпал с ЕСИА | другой кадастр или задача `sales` |
| Объект не прошёл шлюз | другой кадастр или сход |
| ЕСИА / ЦПГ недоступны или отказ по цели | ручная анкета + OCR |
| `PrescoringNegative` / `Failed` | очередь `sales`, не оффер |
| `PrescoringBankDeclined` | закрытие, экран отказа |
| Покупка или рефинансирование на экране 2 | другой сценарий; этот документ не действует |

## 6. Вне минимума v1

- Рефинансирование (обременение другого банка, долг, банк рефинансирования)
- Созаёмщик через ЕСИА
- Несколько предметов залога
- Доход из ЦПГ для ПДН без справки
- Вид сведений «недвижимость» в ЦПГ — если банк подключит, может заменить ввод кадастра
- Автоодобрение АНД/АПЗ без человека — только если так решит Loginom; оркестратор не подменяет СПР
- Скоринг (`getDecision`) на экране 6 нет: он считается Loginom и показывается в АРМ банка (AS-IS — ELMA). Solver после скоринга не вызывается

## 7. Доп. условия (ДУ) — не ломают экраны 1–6, но возвращают клиента после АНД

Справочник AS-IS: `ElmaAdditionalConditionTypeEnum` 0–18. В ЛК два контура, не путать:

| Контур | Где | Когда |
|--------|-----|--------|
| Виды ДУ (`additional_conditions`) | список на паспорте сделки | приходят с решением Stage-3 |
| Чек-лист (`checklists_items`) | загрузка файлов, `GET/POST …/checklist` | ELMA шлёт конкретные документы на исполнение |

ДУ **не** входят в прескоринг и **не** отменяют `combined`. Combined пропускает только стартовый сбор анкеты. Если АНД/АПЗ выставили условия — клиенту снова нужна форма: загрузить файлы или выполнить действие. Без снятия ДУ в AS-IS не подписывают КОД (Visio: «ДУ сняты?» → иначе возврат на процессинг; часть ДУ можно перенести на выдачу / аккредитив).

| Тип | Текст в ЛК | Кто действует | Влияние на клиентский путь v1 |
|-----|------------|---------------|-------------------------------|
| 0 | Финансовый документ | клиент | самый частый возврат после «без справок»: 2-НДФЛ и т.п. |
| 1 | Документ клиента | клиент | догрузка не из ЕСИА |
| 2 | Документ по объекту залога | клиент | ЕГРН на входе уже есть; АНД может всё равно просить оригинал / техпаспорт |
| 5, 8, 18 | Брак, согласие супруга, нотариальное согласие | клиент | ЕСИА v1 семью не отдаёт; всплывёт на АНД |
| 6, 7 | Смерть / расторжение брака | клиент | то же |
| 11 | ПНД/НД или ВУ / разрешение на оружие | клиент | не из профиля |
| 16 | Значимый актив | клиент | |
| 9, 15 | Подтверждение погашения кредита / просрочки | клиент | документы; в v1 без рефина всё ещё возможны другие долги |
| 3, 12, 13 | Погасить кредит, долг ФССП, консолидация | клиент (действие) | не файл, а факт оплаты; 12 связан с негативом прескоринга |
| 14 | Погашение после сделки | сделка / выдача | не блокирует вход, блокирует или сдвигается к выдаче |
| 4 | Согласование Правлением | банк | клиент ждёт, ничего не грузит |
| 10 | Контроль погашения кредита | банк | внутренний контроль |
| 17 | Не удалось получить ФССП | банк / повтор | не клиентский экран |

В форме подачи после `prior_approve` нужен экран «условия банка» (наследник чек-листа ЛК), иначе combined создаёт иллюзию, что после пакета Solver клиент больше ничего не делает. Лаб v1.2 этого экрана нет — gap прода.
