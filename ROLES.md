# ROLES.md — роли и что где смотреть (LAB)

Демо-режима в лаборатории нет: ни автологина по адресу, ни автосброса, ни скрипта
ведущего, ни страницы подготовки показа. Кабинет и столы открываются обычным
адресом и меняются только от действий человека.

## Логины

| Роль | Доступ |
|------|--------|
| Клиент | `+7 (999) 123-45-67` / `password123` |
| Менеджер | `admin` / `manager123` |

SMS/OTP — любой код. Госуслуги — имитация. Столы сделки, андеррайтера, участника
комитета и продуктолога входа не требуют: в АРМе участника комитета роль

## Как начать

1. Откройте кабинет: `index.html`. Введите телефон и пароль, нажмите **«Войти»**,
   затем **«Войти в личный кабинет»**. Это единственный способ входа.
2. Менеджер **в той же вкладке браузера**: `manager/`, логин `admin`, пароль
   `manager123`, кнопка «Войти». Он видит ту же заявку, что собрал клиент.
3. Столы `deal-ops/`, `underwriter/`, `productolog/` открываются сразу и ведут
   своё хранилище. Кнопка **«Сбросить сцену»** в шапке стола возвращает только
   его сцену к началу — кабинет клиента она не затрагивает.
4. После выкладки Pages подождите ~10 минут или **Ctrl+F5**. Режим инкогнито **не** обходит CDN GitHub Pages.
5. Один браузер, две вкладки (общий `localStorage`). Split-view нет.

Проверка перед показом: `node scripts/run-all-checks.js` — одной командой (аудит, формы и все шесть поверхностей). Возвращает код 1 при провале любого шага.

## Happy-path (5–7 мин)

1. Клиент: вход → **Мои заявки** → №4421-И → таймлайн этапов → **Продолжить оформление**.
2. Объект залога → **ЕСИА** → прескоринг → сравнение пакетов (переплата) → «Турбо 2.0» → принять / печать оффера.
3. При необходимости: **Загрузить** «Выписка ЕГРН» в карточке заявки.
4. Чат → менеджер.
5. Менеджер: скоринг (быстрый + зелёный по умолчанию) → одобрение → тост у клиента.

### Негативный скоринг (опционально)
Снять галочку **«Зелёный скоринг»** в шапке менеджера — возможны проблемы/отказ на шагах.

## АРМ сделки (открытие счёта, мок)

`/deal-ops/`. Это не ELMA: стол ОЗС после КОД. Госуслуги на сделке не открываем — ЕСИА это флаг с заявки. На карточке этапы по-русски (Клиент → Счёт → Проверки → Заявление → Подпись → АБС → ДБО). Иконка **i** у блока — зачем он и какой следующий шаг.

Электронная форма клиента (то, что в SMS): `/deal-ops/account-app.html?t=25BGFB00990001`. Полная СОПД по SMS: `/deal-ops/sopd-app.html?t=25BGFB00990002`. Хранилища: `bgfbank_lab_account_app`, `bgfbank_lab_sopd`.

Фильтр очереди: **Все / ЕСИА / без ЕСИА**. Признак ЕСИА в карточке **всегда** виден (`ЕСИА: да` или `ЕСИА: нет`), независимо от сценария СОПД. СОПД и ЕСИА не связаны: канал первого согласия — как его получили (`partner` / `manager` / `sms`), не вход в Госуслуги.

| Заявка | СОПД (первое) | ЕСИА | Что показать |
|--------|---------------|------|--------------|
| `25BGFB00990001` | SMS, полная электронная, действует | да, объект счёта к подписанию | Шаблон полной **скрыт**. Сверка с ЦПГ. SMS-заявление → счёт **после** КОД. Электронная: УКЭП есть / выпуск → клиент и банк → `KodSigned` (не Росреестр) |
| `25BGFB00990002` | партнёр, короткая | нет, объект к подписанию | Добор полной СОПД. Бумага: печать/сшив. Счёт **до** КОД. Выдача **после** госрегистрации |
| `25BGFB00990003` | менеджер, полная бумага, **просрочена** | да, счёт уже открыт | Шаблон полной / SMS; заявление на открытие пропускаем |
| `25BGFB00990004` | SMS, полная, действует | нет | Автопроверки: ИНН `error` → **ОПЕРУ**. Согласовать → ОЗС; отказать → стоп |

1. Выбрать заявку. В блоке СОПД: первое касание (лид ELMA), форма/версия/срок/канал, «Скачать и проверить»; добор полной — SMS (`sopd-app.html`) или бумага за столом. Пока СОПД недостаточно, «Искать счёт в ЦФТ» неактивна. Дата лида в шаблон не идёт.
2. Отметить идентификацию и телефон.
3. «Искать счёт в ЦФТ» — `FindRetailAccount`; если счёта нет — шесть автопроверок. У `…004` ИНН даёт `error` → очередь ОПЕРУ (`checks_operu`); согласовать возвращает ОЗС, отказать — `stop_factor`. Шина показывает статус callback (`ELMA ← {"deal_id","status"}`).
3. **Канал A:** «Отправить ссылку» (`AccountAppLinkSent`) → «Открыть форму клиента» → любые 4 цифры → `AccountAppSigned` в шине АРМ.
4. **Канал B:** «Печать шаблона» → загрузить любой файл как скан.
5. Снять ДУ «до подписи КОД». **Электронная** (`…001`): УКЭП уже есть **или** заявление на выпуск → «Клиент подписал КОД» — пакет комплекта (не обращение в Росреестр) → клиент → банк → `KodSigned` → если счёт ещё не открыт, `OpenAccount`. **Бумага:** сначала «пакет напечатан и сшит». `…002` по умолчанию открывает счёт **до** КОД; `…001`/`…004` — **после**. Кнопки «Правки КОД → процессинг» и «Отказ клиента». Сканы — галка после подписи, не блокируют `KodSigned`.
6. Заявление ДБО + приложение 1, затем «Клиент открыл ДБО» — готово к выдаче ОБУКО, без второго окна.

## АРМ андеррайтера (АНД / АПЗ)

`/underwriter/`. Это не кабинет и не стол ОЗС: две очереди после СБ. Человек — АНД, объект — АПЗ. Роли переключаются кнопками в шапке. Паспорт сделки здесь не открываем.

Хранилище: `bgfbank_lab_underwriter`. Стол не зовёт Loginom сам — только оркестратор на шине (`getDecision`, `getPdn`, `getEval`).

| Заявка | Очередь | Что показать |
|--------|---------|--------------|
| `25BGFB00990101` | АНД | Комплект → скоринг → авторешение → **Клиент одобрен**. Звонка нет (автоодобрение + LTV 48%). Барьер: АПЗ уже «залог одобрен» |
| `25BGFB00990102` | АНД | ФССП 180 тыс → `FSSP_001`, надбавка +2 п.п., опция «Зелёный коридор» (не 4-я цель), ДУ 12, кнопка **Расчёт**, звонок, затем одобрение или КК |
| `25BGFB00990103` | АПЗ | ЕГРН как файл+OCR → Express/`getEval` → **Залог одобрен**. Заёмщик уже «клиент одобрен» |
| `25BGFB00990104` | АПЗ | Коммерция: внутренний оценщик + КК, затем одобрение |

Панель **Кредитный комитет** появляется у заявок, которые вынесены на комитет
(у `…104` — сразу, по признаку коммерции). Заседание собирает система: состав по
признакам заявки, слот из графика. Дальше — **Подтвердить заседание**,
**Открыть заседание**. В окне: уровень решения (Комитет → Правление → Совет
директоров), состав с пометкой обязательных, позиции, кворум и три исхода.
Пока обязательные не дали позицию, «Одобрить» и «Отказать» заперты, а «Не
согласен» без причины не принимается. **Эскалировать выше** поднимает заседание
на следующий уровень и сохраняет след нижнего.

## АРМ участника кредитного комитета

`/underwriter/kk-member.html`. Куда падает приглашение: участник выбирается
переключателем в шапке (или адресом `?member=m_appraiser`). Своей сцены у
поверхности нет — она читает и дописывает сцену стола андеррайтера
(`bgfbank_lab_underwriter`), поэтому позиция сразу видна в окне заседания, а
приглашение появляется только после подтверждения заседания в столе.

Отдельного входа на карте демо у этого АРМа нет и быть не должно: пока заседание
не подтверждено в столе, приглашать некого, и карточка на карте открывалась бы в
пустое «приглашений нет». Ссылка **АРМ участника комитета** живёт в панели
комитета на карточке заявки — оттуда и открывается.

1. В столе: **АПЗ** → `…104` → **Подтвердить заседание** → **Открыть заседание**.
2. В АРМе участника: выбрать участника → **Подтвердить участие** → выбрать
   позицию → причина (обязательна для «Не согласен» и «Отсутствую») →
   **Отправить позицию**.
3. Вернуться в стол: в панели комитета счётчик позиций обновился, а в окне
   заседания позиция участника уже стоит.

ФИО участников и дежурных вымышленные: настоящих сотрудников банка в макете нет.

## АРМ продуктолога и риск-менеджера

`/productolog/`. Не очередь сделок и не кабинет партнёра: справочник, который читает калькулятор предложений. Рабочий канон условий — **OnePage** (лист = цель, колонка = пакет, строки КИ1–КИ5). Три цели — покупка, залог, рефинансирование. «Зелёный коридор» — отдельная карточка-опция по листу OnePage, не четвёртая цель. Макет Figma устарел: из него оставляем варианты выдачи, статусы и регионы.

Роли шапки: переключатель **Продуктолог** / **Риск-менеджер** на той же странице `/productolog/` — кнопками, как АНД/АПЗ у андеррайтера. Отдельный адрес не нужен: `?arm=risk` остался только как альтернативный вход в роль риска. У продуктолога вкладки **Продукты** · **Опции** · **Регионы**. У риск-менеджера — **Риск** · **Матрица**. На продукте вкладка **Условия** — пакеты, сетка КИ, срок, возраст, страховка, доля кредита объект × география. Проценты помечены как снимок, не офер калькулятора. Категорию КИ назначает СПР. ДОМ.РФ и инвесты не становятся целью. **Варианты выдачи** (не 4-я цель): статус включая **Заполняется** / **Не принято рисками**, справка о доходах, трудовой статус, регион, объект, размер города; сорт от новых к старым; черновик «Создать черновик». **Опции** — CRUD записей (не отдельная цель, этап лид, надбавка к комиссии только с периодом акции; повесьте на якорь, затем откройте регион). **Регионы** — карточка **Доступность**: матрица опция × регион на выбранном якоре. Клетка витрины = продукт доступен И регион открыт И якорь продаётся в городе И опция повешена И галка включена. Казань без покупки, Саратов без «купи ставку». Кнопка **Добавить регион** — новый город без якорей, затем продукты и опции. Карточка города: название, якоря и мини-матрица опций по продуктам; сетка доли кредита из листов LTV OnePage. **Риск**: колонки От / До / Балл, ряд **нет значения**, границы 0 и «без ограничения» не удаляются; «Посчитать балл» остаётся в лабе. **Матрица**: фильтры канал/регион/тип/оси (доля кредита × оценка по риску) — только якоря, которые продаются в городе; ячейки только для чтения, прочерк для дырки, автонастройка шагов. Таблица — только файл .xlsx. Админку сотрудников и калькулятор партнёра не тащим. СПР из этого стола не вызываем. Хранилище: `bgfbank_lab_productolog` (версия 6).

## Не кликать на сцене

- Регистрацию нового пользователя.
- Standalone `scoring_negative.html`.
- Повторный прескоринг после принятого пакета без нужды.

## Если залипло

- Клиент: **Новая заявка** на клиенте.
- Стол: кнопка **«Сбросить сцену»** в шапке — она возвращает к началу только этот стол.
