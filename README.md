## Проверки перед показом

Одна команда запускает всё: статический аудит разметки, браузерный прогон форм
клиента и прогон шести поверхностей лаборатории (кабинет клиента, АРМ менеджера,
стол сделки ОЗС/ОПЕРУ, АРМ андеррайтера, АРМ участника кредитного комитета,
стол продуктолога).

```bash
node scripts/run-all-checks.js
```

Три шага идут последовательно (аудит разметки → формы клиента → кабинеты и столы),
каждый печатает свой итог, в конце — общий. Код возврата: **0**, если прошли все
шаги, **1**, если провалился хотя бы один.

Отдельные шаги, если нужен только один:

```bash
node scripts/pre-release-audit.js               # разметка, ссылки, общий слой форм — 551
node scripts/form-flow-check.js                 # обе формы клиента — 96
node scripts/surface-check.js                   # шесть поверхностей — 548
node scripts/surface-check.js --only=cabinet    # одна поверхность — 64
```

Обычный прогон (без `--base`) поднимает локальный сервер, запускает headless
Chrome и проходит сценарии как пользователь: ввод, клики, галочки, ползунки,
перезагрузку с возвратом на сохранённый шаг и отправку заявки. Внешних
зависимостей нет — DevTools Protocol и встроенный в Node `WebSocket`;
`package.json` в репозитории нет.

### Что такое поверхности и что покрыто

Поверхность — это страница или стол, который проверяется целиком. Раннер
`scripts/surface-check.js` идёт по списку и для каждой поверхности вызывает свой
файл `scripts/checks/<ключ>.js`.

| Поверхность | Ключ `--only=` | Проверок |
|-------------|----------------|----------|
| Кабинет клиента | `cabinet` | 64 |
| АРМ менеджера | `manager` | 92 |
| Стол сделки ОЗС / ОПЕРУ | `deal-ops` | 122 |
| АРМ андеррайтера (АНД / АПЗ) | `underwriter` | 131 |
| АРМ участника кредитного комитета | `kk-member` | 33 |
| Стол продуктолога / риск-менеджера | `productolog` | 106 |
| Формы клиента (потребительский кредит + залог) | `forms` | 96 |
| Аудит разметки (без браузера, не поверхность) | — | 551 |

`--only` принимает и список: `--only=cabinet,forms` даёт 64 + 96 = 160.

**Почему без `--only` выходит 548, а не 644.** Прогон `surface-check.js` без
`--only` идёт по списку шести поверхностей (`DEFAULT_SURFACES`,
`scripts/surface-check.js:49`), и форм в нём нет: у форм свой отдельный шаг в
`run-all-checks.js`, иначе в единой команде они считались бы дважды. Поэтому
`node scripts/surface-check.js` даёт 548, а с `--only=forms` — 96. В карте
поверхностей формы остаются, так что `--only=forms,cabinet` работает как обычно.
Прогон без `--only` пропусков не даёт: за все шесть поверхностей есть файлы.

### Опции прогонов

| Опция | Что делает |
|-------|------------|
| `--only=<поверхность>` | прогнать только выбранные поверхности (`surface-check.js`), можно списком через запятую |
| `--base=<url>` | гонять проверки по опубликованному сайту вместо локальных файлов: локальный сервер не поднимается |
| `--chrome=<путь>` | путь к Chrome или Edge; без него браузер ищется в стандартных местах и в `CHROME_PATH` |
| `--port=<порт>` | порт локального сервера (по умолчанию 8110, у прогона форм 8123; порт CDP = порт + 1) |
| `--keep` | не закрывать браузер и не удалять профиль после прогона — для разбора упавшей проверки |

Пример прогона по живому адресу:

```bash
node scripts/form-flow-check.js --base=https://aleshafaceman.github.io/bgfbank-credit-conveyor-lab
```

Если сразу после выкладки Pages прогон по `--base` падает, а страница при этом
выглядит обновлённой — это расхождение кэша Pages по узлам. Подождите минуту и
повторите: прогон сам добавляет параметр обхода кэша, но CDN успевает обновиться
не везде одновременно.

### Устройство

- `scripts/lib/browser-check.js` — обвязка: локальный сервер, запуск headless
  Chrome, клиент DevTools Protocol, помощники страницы (`__t.*`) и монитор сбоев
  (`__bgfFailures`).
- `scripts/checks/*.js` — проверки поверхностей, по файлу на поверхность;
  `scripts/checks/common.js` — общие помощники (`why`, `noFailures`).
- `scripts/run-all-checks.js` — единая точка входа: три шага подряд.
- `scripts/form-flow-check.js` — тонкая обёртка над `scripts/checks/forms.js`.

### Две оговорки, найденные на практике

- **Не обрезайте вывод прогонов пайплайном** (`| Select-Object -First N`,
  `| head`): процесс убивается до того, как закроет сервер, Chrome и профиль, и
  в `%TEMP%` остаются висеть процессы Chrome и каталоги `bgf-flow-profile-*`.
  Перенаправляйте вывод в файл: `node scripts/surface-check.js > out.txt 2>&1`.
- Проверки разных поверхностей идут **в одном браузере и на одном origin**,
  поэтому состояние, оставленное одной проверкой, видит другая. Если пишете новую
  проверку, не сравнивайте весь `localStorage` — сравнивайте разницу до и после.
